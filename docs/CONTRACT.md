# Personal v1 implementation contract

The accepted NAS deployment extension is defined in [NAS-CONTRACT.md](NAS-CONTRACT.md). Graph semantics remain unchanged; optional OAuth authentication, bounded scheduling, configured capacity guards and separate TLS listeners are implemented. Current executed checks and deployment limits are recorded in [acceptance evidence](ACCEPTANCE-RESULTS.md).

Selected for implementation on 7 November 2026 after the owner answered Q7–Q10 and explicitly said “Proceed”. This authorizes the coordinated build; it does not assert completed qualification or authorize live personal-data ingestion, external deployment, software installation, or credential changes. Linear stays paused.

Q7: clients proactively capture useful knowledge within configured grants. Q8: explicit authenticated owner corrections are preferred while contrary claims/evidence remain visible. Q9: MCP and CLI first; no browser UI in v1. Q10: prove project decisions and rationale, person/relationship evidence, and changes since last month. Capture is client-driven; the server does not monitor unrelated files/conversations or call an external model.

## Runtime and boundaries

Python 3.12+ standard library and SQLite WAL with synchronous FULL. One database per personal peer; no shared database file. A transaction admits each immutable operation group, its local application position and projections atomically. SQLite is chosen for portable transactions, backups and operational simplicity, not as a winner extrapolated from the earlier selective-read benchmark. Core operation needs no third-party runtime dependencies. The optional OAuth resource profile uses the declared PyJWT/cryptography dependencies; its maintained authorization server is a separate deployed component. CI installs the pinned test dependencies. Protocol implementation is checked against official MCP and available real clients.

Direct personal sync uses authenticated HTTPS (numeric loopback HTTP only for local tests). Each admitted origin has an HMAC-SHA256 key. The other admitted personal peer can verify the original operation; this shared-secret design does not provide nonrepudiation against a malicious admitted peer. Client grants and peer admission are local administration, never data operations or replicated authority. Explicit local `admit_recovery_origin(sender, origin, key_hex)` permits a paired restored peer to forward one retained historical origin; it is not unrestricted relay admission. No transitive relay or corporate tenant protocol is claimed.

## Python API for coordinated implementation

`from refactoredmemory.store import Store, MemoryError, ValidationError, AuthorizationError, ConflictError`

- `Store(path, *, store_id=None, peer_id=None)` opens/creates a database. New databases create random identities unless supplied. Existing databases reject mismatched supplied identity. Context manager and `close()` supported.
- `store.submit(actions, *, actor=None, request_id=None)` returns `{operation_id, known_position, action_ids, duplicate}`. Trusted in-process actor defaults to `{id:'owner',kind:'owner'}`. Public transports only use actor resolved from a local grant, never a submitted actor. Request IDs are actor-scoped and conflicting retries fail.
- Actions use discriminator `type`: `entity`, `source`, `assertion`, `delete`, `restore`. Every action has a stable `id`. Maximum 500 actions / 1 MiB operation, 64 KiB text field, bounded identifiers.
- Entity: `{type:'entity',id,entity_type,label}`. Repeating an identical immutable identity is allowed, changing it fails. Names can evolve through assertions.
- Source: `{type:'source',id,uri,content,metadata:{...}}`. Immutable content/version identity. Sources are evidence, never executable instructions.
- Assertion: `{type:'assertion',id,subject,predicate,value}` or `object` (one only); `source_ids:[id,...]`, `kind:'assert'|'correct'|'retract'|'invalidate'|'reinstate'`, `predecessors:[assertion_id,...]`, `reason`, `valid_from`, `valid_to`, `time_precision`, `provenance:{...}`, `uncertainty`. Subject/object/source/predecessor references must exist in this group or a causally applied earlier group. Semantic actions other than assert require predecessors and reason; lineage subject/predicate is stable. Unknown fields are rejected on semantic actions; metadata/provenance allow bounded JSON.
- World dates use ISO UTC timestamps or YYYY-MM-DD. Intervals are half-open. Missing `valid_to` means ongoing; explicit null means unknown. Missing/null `valid_from` means unknown. Untimed claims are returned unfiltered with uncertainty, but a valid-at query returns only definite matches and reports excluded unknown-time coverage. `time_precision` is exact/day/approximate/unknown; approximate intervals do not claim definite exact-time matches.
- `store.query(*,subject=None,predicate=None,object=None,text=None,valid_at=None,known_at=None,frontier=None,include_inactive=False,limit=100,offset=0)` returns `{assertions:[...],coverage:{...},frontier,known_position}`. Assertions include trusted actor, local known position, operation ID, status, preferred, conflicts and source IDs. `known_at` is this replica's integer application position; `frontier` is a causally closed `{origin:sequence}`. Supplying both fails. Unknown/out-of-range positions/frontiers fail rather than pretend complete coverage. Limit <=1000.
- Current heads derive from visible predecessor links; no clock winner. Retraction withdraws a belief from current knowledge without inventing a world endpoint. Invalidation supplies an explicit valid_to and preserves the relationship in its earlier half-open valid interval; it is an ended historical claim, not a retraction. Owner correction preference comes from trusted actor.kind and kind=correct. A later inferred descendant does not hide an owner correction; a later explicit owner action may supersede it. Independent contradictory claims remain visible. Human verification is not inferred from successful admission.
- `store.history(entity_id=None, *,since=None,known_at=None,limit=100)` returns admitted operations and their local knowledge positions, bounded and with coverage. `since` is an exclusive replica position or ISO receipt-time lower bound; use explicit frontier/position for repeatable change queries.
- `store.traverse(start, *,depth=2,limit=100,valid_at=None,known_at=None,frontier=None)` returns `{entities,edges,coverage,frontier,known_position}`; max depth 8, bounded breadth. It applies the same assertion/temporal rules as query.
- `store.read(kind,id)` returns raw immutable entity/source/assertion payload for local import planning. `store.get_source(source_id)` and `store.get_entity(entity_id)` return evidence/identity; deleted entities are suppressed from ordinary reads/history unless administrative export is explicitly used.
- Delete: `{type:'delete',id,entity_id,reason}`. Restore: `{type:'restore',id,entity_id,predecessors:[delete_action_id,...],reason}`. Tombstones are administrative suppression, independent of factual history. Unseen/concurrent deletes continue suppressing; stale writes cannot restore.
- `store.status()` returns store_id, peer_id, frontier, known_position, pending, counts, storage profile and visible conflicts. `store.rebuild()` rebuilds projections atomically from applied journal history. `store.backup(path)` makes a SQLite consistent backup (no overwrite).
- `Store.restore(snapshot_path,destination,*,peer_id=None)` restores graph/history into a fresh peer identity, with no active client grants or peer admissions; originals unchanged. The restore verifies signed journal identity, contiguous positions/sequences, causal closure and projection consistency, rejects executable SQLite schema objects, then replays into a fresh schema. Original replica receipt metadata is retained separately in inherited_receipts; the new replica receives the inherited history at restoration time. Query coverage identifies the inherited prefix, so copied historical positions do not pretend the new device learned data earlier. Current admitted peers must explicitly admit the new identity and reconcile newer tombstones before use; an offline stale backup alone cannot know future deletions/revocations.

## Peer and service APIs

- `store.identity()` returns local peer_id/store_id and signing key for explicit local pairing only; never expose through MCP. `store.admit_peer(peer_id,key_hex)` and `store.revoke_peer(peer_id)` are local administration.
- `store.export_operations(frontier=None,limit=100)` returns `{operations,frontier,more}`; only applied operations exported. Export includes original signature. `store.receive(operations,peer_id)` authenticates admitted sender and origin, detects conflicting identities, stores durable receipt and applies groups only after dependencies; returns `{received,applied,pending,frontier}`. Pending receipt is not acknowledged as causal application.
- `store.create_grant(label,scopes,*,kind='agent',peer_id=None)` returns a new opaque token string once. kind='peer' requires an admitted peer_id and only sync scope. Local scopes: read/write/correct/admin/sync; owner-kind grants only via local administration. `store.revoke_grant(token)` removes access. `store.authenticate(token,scope=None)` returns trusted `{id,kind,scopes}`; revoked grants fail even for old historical queries.
- `Service(store, authenticate=None)` in `refactoredmemory.service` exposes `tools()->list`, `auth(token,scope=None)->actor`, `call(name,arguments,token)->dict`. The default callback is Store authentication; the OAuth callback validates the access token and intersects its scopes with the current bound local agent grant. `auth` checks active token for discovery/list. `call` checks each tool scope, strict argument schema and sanitizes authority fields. Mutation payloads may not forge actor, owner correction flags, human review or grant metadata.
- MCP dispatcher: `Dispatcher(service).dispatch(message,token)`; `run_stdio(service,token)`; `make_handler(service,allowed_origins=())`. The local `serve` profile composes `/mcp` with `/sync`; `serve-nas` uses separate TLS listeners and does not expose `/sync` on the public MCP listener. Explicit `--allow-legacy-http` enables the tested 2025-11-25 lifecycle without weakening modern per-request validation.
- Sync POST `/sync`: bearer token with dedicated sync scope and local binding to admitted peer_id. JSON `{protocol:'refactoredmemory-sync/1',store_id,frontier,operations,limit}`. Response `{protocol,store_id,peer_id,operations,frontier,more,receipt}`. Authentication binds sender to peer, never a caller supplied actor. `sync_once(store,url,token,batch_size=100)` in sync.py returns bounded exchange stats. HTTPS verification required outside numeric loopback; no credential forwarding across redirects.

The optional `OAuthAuthenticator(store, config_path)` accepts only pinned HTTPS issuer/resource policy and locally supplied RS256 JWKS. Access tokens require a recognized access-token marker, exact subject/client binding and a lifetime no greater than 300 seconds. Default clock skew is 5 seconds, configurable up to 30. JWKS and owner-only grant files are reread per call; issuer/bindings remain startup-fixed. `memory:read`, `memory:write` and `memory:correct` map to current local scopes; owner/peer grants cannot bind. RFC 9728 metadata and safe 401/403 challenges support resource discovery; token issuance, login and client registration belong to the maintained AS.

`store.configure_capacity(min_free_bytes=..., max_store_bytes=...)` enables conservative process-local graph-write guards. `serve-nas`, `sync-watch`, applied CLI imports and owner submissions set them from their configuration; direct Store callers must opt in explicitly. The store ceiling covers allocated SQLite pages, while free-disk checks reserve estimated WAL/index growth; neither is a whole-filesystem quota. Audit/status files are bounded or replaced atomically and do not hold source content or credentials.

All access and integrity checks remain current. Missing Mac access, original legacy archives or full application qualification stays explicit in release evidence; synthetic local-process tests are not relabelled as those results.

## Implemented recovery and attribution details

Duplicate identical immutable records can be submitted on both peers. Each operation occurrence is retained, and a query chooses deterministic attribution among the occurrences visible at its selected frontier while retaining all attributions. Such copies do not create independent evidence. Supersession is computed before current administrative output suppression; deleting a corrected endpoint cannot resurrect a superseded claim.

Restore uses a fresh identity and clears local admission/grants. A survivor must explicitly permit the restored sender to forward each retained historical origin with its original verification key. The restored side may need the reciprocal recovery permission for post-snapshot operations from a retired origin. Until synchronization reconciles current deletion/grant state, a disconnected stale copy cannot establish current authority or complete knowledge. See SYNC-PROTOCOL.md.
